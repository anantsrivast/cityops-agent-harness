# CityOps Agent Harness — A Narrated Walkthrough

A guided tour of *why* this project exists and *how* each notebook works. Read it
top to bottom for the argument, or jump to a notebook. Diagrams show the real
mechanism, not a cartoon of it.

---

## 0 · The premise: why this project exists

The prerequisite workshop built the **CityOps Copilot** — an inspection agent with
memory. A design review of that copilot found that its memory worked in the demo
but would rot over a long horizon. Three failures, in the review's words:

> *promotion without curation · success without verification · growth without forgetting*

This project is the **harness** that fixes those failures and, crucially, **proves
it did** with an eval suite. Everything durable lives in **Oracle Autonomous
Database** (rows, vectors, scheduled jobs), and embeddings run **inside** the
database (ONNX), so no text ever leaves for a third-party embedder.

### Two memory paths

The review's failures split across two independent ways an agent accumulates
memory. Each notebook fixes one path and then measures it.

```mermaid
flowchart LR
  CP["CityOps Copilot<br/>(prerequisite)"] --> N0["00 · Setup"]
  N0 --> N1["01 · Self-improving copilot<br/><b>Path 2: procedures → skills</b>"]
  N1 --> N2["02 · Curated long-term memory<br/><b>Path 1: scratch → long-term</b>"]
  N2 --> N3["03 · Context engineering<br/><b>what the window holds</b>"]
  N3 --> N4["04 · Evals<br/><b>prove all of the above</b>"]
```

- **Path 2 (notebook 01)** — the agent turns *what it did* into reusable **skills**.
  Gaps fixed: capture the full trajectory (not just tool names), verify success
  against the database (not the prose), and let skills earn authority over time.
- **Path 1 (notebook 02)** — scratch notes **graduate** into long-term memory. Gaps
  fixed: curate before promoting, record provenance, let new facts supersede old
  ones, and actually schedule the pipeline.
- **Context (notebook 03)** — the working window itself: compaction and offloading,
  measured for **fidelity, not size**.
- **Evals (notebook 04)** — five experiments that grade exactly the gaps above.

### The architecture: two layers

A single idea shapes every notebook. **Decisions are pure; effects are in the
notebook.**

```mermaid
flowchart TB
  subgraph L1["src/cityops_harness — pure decision logic (offline, unit-tested)"]
    improve["improve.py<br/>merge/harvest/lifecycle"]
    promote["promote.py<br/>gate policy/recency/health"]
    context["context.py<br/>compaction/offload/strength"]
    evals["evals.py<br/>precision/variance/cost"]
  end
  subgraph L2["notebooks — side effects (generated by tools/make_0X.py)"]
    sql["SQL / DDL / DBMS_SCHEDULER"]
    llm["LLM + judge calls"]
    lf["Langfuse traces"]
  end
  L2 -->|"import the decisions"| L1
```

Why this matters: the *rules* (when to merge, when to promote, how to score) are
~450 lines of side-effect-free Python with **53 unit tests** that need no DB, no
LLM, no network. The notebooks wire those rules to Oracle and the model. When a bug
appears, it's almost always in the wiring — the rules are provable in isolation.

Two more conventions worth knowing:

- **Generated notebooks.** Each notebook is emitted by a `make_0X_notebook.py`
  script, and `make_student.py` strips the marked solution blocks to produce a
  learner (`*_todo`) flavor. One source of truth → the two flavors can't drift.
- **Independently runnable.** Every notebook opens by verifying the artifacts its
  predecessor should have left (`state.require`), with an idempotent backfill — so
  each runs alone, but continuity across them is itself the lesson.

## 1 · Notebook 00 — Setup

**Why:** fail fast and specifically. Every later notebook assumes a working
database, an in-DB embedding model, a reachable LLM, and (for notebook 04)
Langfuse. Notebook 00 checks each and ends every section with a green tick, so a
broken environment surfaces here — not five cells into notebook 02.

**How:** four probes.

| Section | Verifies | The subtle part |
|---|---|---|
| ADB connectivity | a pooled connection + `v$version` | `db.py` pools at 2 connections/process; the ADB caps at 30 sessions total |
| In-DB embeddings | `ALL_MINILM_L12_V2` loads and embeds | idempotent — re-running skips a present model |
| LLM provider | one `LLM_PROVIDER` drives both consumers | LangChain chat **and** the LiteLLM SDK path |
| Langfuse | `off` / `local` / `cloud` | optional for 00–03; **required** by 04 |

The reason one env var (`LLM_PROVIDER`) is emphasized: the same switch feeds two
different clients — LangChain (for agent/chat calls) and LiteLLM (for the Oracle
Agent Memory SDK). Notebook 00 constructs both so a provider misconfiguration is
caught once, here.

## 2 · Notebook 01 — The self-improving copilot (Path 2)

**Why:** the review's Path-2 verdict was that the original harness "learned" from a
*sorted set of tool names* and called any run with a final answer a success. You
can't distill a reliable procedure from a set of names, and you can't trust a
success you never checked. This notebook rebuilds learning so it's grounded and
verified.

The full cycle is `run_and_learn`: **act → judge → capture → harvest**, all inside
one trace.

```mermaid
flowchart LR
  task["task"] --> act["run_copilot_task<br/>(agent loop)"]
  act -->|"trajectory + answer"| judge["judge_workflow<br/>(verified success)"]
  judge -->|"verdict"| cap["capture_workflow<br/>(gray-band dedup)"]
  cap --> harv["harvest<br/>(recurs + verified → SKILL.md)"]
```

### 2.1 · Tools: a hot core, the rest disclosed on demand

Two tools are always bound — the search → log core that covers the common task.
The rest sit in **capability groups**, each with a *when to reach for it* line
that goes into the agent's instructions as a routing rubric. A meta-tool,
`open_capability(group)`, unlocks one; the toolset is re-bound every turn, so the
group's tools are callable on the next step. `HARNESS_TOOLS` is a catalogue by
group — no embeddings.

The point is **legibility**. An earlier version embedded tool descriptions and cut
by cosine distance, which failed silently: a differently-worded task lost a tool
it needed and nothing said so. Here the agent asks for the capability by name, the
request is a visible step in the trajectory, and a wrong guess costs one turn and
self-corrects.

### 2.2 · The agent loop captures the *full* trajectory

```mermaid
sequenceDiagram
  participant Task
  participant Agent as Agent (LLM)
  participant Tools
  participant DB as Oracle DB
  Task->>Agent: task + hot tools + capability rubric
  loop until no tool calls (max_iters)
    Agent->>Tools: tool call (args)
    Note right of Agent: open_capability → toolset re-bound next turn
    Tools->>DB: read / write
    DB-->>Tools: result
    Tools-->>Agent: full result
    Note right of Agent: trajectory += {tool, args, full result}
  end
  Agent-->>Task: final summary
```

Every step records the **tool, its arguments, and its full result, in order** —
the record the judge audits and skills distill from. A tool error becomes `ERROR:`
text in the message, not a crash, so the model can recover *and* the failure stays
visible in the trajectory.

### 2.3 · Verified success: the judge audits the database, not the prose

This is the heart of the Path-2 fix. `success = bool(final)` let confident nonsense
pass. Instead:

```mermaid
flowchart LR
  ans["final answer"] --> ev["build_evidence:<br/>re-query every cited finding_id"]
  ev -->|"EXISTS / NOT FOUND"| J["LLM judge"]
  traj["trajectory"] --> J
  ans --> J
  J --> V{"verified?"}
  V -->|yes| S["verified_successes++"]
  V -->|no| F["failures++"]
```

`build_evidence` scans the final answer for `finding_id`s — the one it just recorded
plus any priors it cites — and re-queries `CITY_INSPECTION_FINDING` for each, tagging
it `EXISTS` or `NOT FOUND`. It audits **citations**, not the trajectory's claimed
writes: looking up an id the logging tool just returned only confirms that the insert
inserted, while a fabricated citation is the failure that matters. The judge sees task
+ trajectory + answer + that evidence and returns a structured `verified: bool`. Only
a verified run feeds the success count, and the verdict is logged to Langfuse as a
score.

Read the section as a pattern rather than a `finding_id` trick: verify your agent's
checkable side effect against ground truth — a ticket that exists, a test that
passes, an HTTP 200.

### 2.4 · Capture: dedup by meaning, with an honest gray band

A fixed cosine cutoff both under-merges paraphrases and over-merges neighbours.
`merge_decision` splits three ways and asks the model only in the uncertain band:

```mermaid
flowchart LR
  d["intent distance to nearest workflow"] --> B{"merge_decision"}
  B -->|"< 0.15"| M["merge"]
  B -->|"0.15 – 0.40 (gray band)"| Q["LLM: same recurring task?"]
  B -->|"> 0.40"| N["new workflow"]
  Q -->|yes| M
  Q -->|no| N
```

On merge, a **verified** run increments `verified_successes` and overwrites `steps`
with the latest verified trajectory; an unverified one increments `failures`. That
counter split is what stops a repeatedly-failing task from ever being harvested.
(Honest limitation, stated in the notebook: a phrasing *past* the `new` boundary
still splits silently — the gray band narrows the failure, doesn't remove it.)

### 2.5 · Harvest, and skills that earn authority

`harvest_ready` promotes a workflow only when it **recurs and verifiably works** —
`occurrences ≥ 3 AND verified_successes ≥ 2 AND verified_successes > failures`. A
candidate is distilled from the full trajectory, then a **second model call checks
the distilled steps back against that trajectory**; an unfaithful distillation is
rejected and nothing is written. Skills are then born *provisional* and earn their
authority:

```mermaid
stateDiagram-v2
  [*] --> provisional: harvested (faithfulness-checked)
  provisional --> approved: 2 verified successes, 0 failures
  provisional --> retired: 2 failures
  approved --> retired: 2 failures
```

An approved skill is injected as "prefer this approach"; a provisional one as an
unproven candidate — same retrieval, different prompt authority. Track record is the
*only* authority signal: there is deliberately no freshness check. An earlier
schema fingerprint was cut for fingerprinting the wrong layer (skills contain no
SQL — they are procedures over tools), and the `tools_sha` that should replace it
is designed but unbuilt. See §7.

## 3 · Notebook 02 — Curated long-term memory (Path 1)

**Why:** the review's Path-1 verdict — *"everything graduates within the hour, 200-
word chunks get re-extracted into confident misreadings, nothing has provenance,
nothing is forgotten, and the consumer is never actually scheduled."* This notebook
rebuilds scratch→long-term promotion as a **curated, provenanced** step with real
supersession, and ends in a morning briefing built only from **current** memory.
Scheduling is deliberately out of scope: it is orchestration, not memory.

The scratch store is a small filesystem-in-a-table: each note is a row with a
**path** (a policy label), content, and a status.

```mermaid
flowchart LR
  w["remember() / write_note()"] --> SC[("HARNESS_SCRATCH<br/>status = N")]
  SC --> PN["promote_note(path)"]
  PN -->|"outside /inbox"| DD["status D"]
  PN -->|"/inbox"| TG{"store's extraction<br/>(our curation instructions)"}
  TG -->|kept| PR["one verbatim memory in CITY_MEMORY<br/>+ provenance metadata · status P"]
  TG -->|dropped| DD
```

### 3.0 · Where notes come from: the copilot as a producer (§2b)

Before the pipeline runs, the copilot itself files notes. It gets a `remember(asset_id,
note, durable)` tool and one read-only search tool. The design choice worth
internalizing: **the agent is never told about directories.** It judges only *"is this
worth keeping?"*; the tool files `durable=True` into `/inbox` (the opt-in area) and
`durable=False` into `/work` (scratch). Placement is policy the tool owns; the agent
supplies judgement. Its notes then go through the same staging and curation as the
hand-seeded ones. (This section lived in notebook 01 as §8b until 2026-10-19; it moved
here because notes are notebook 02's kind of memory, not notebook 01's.)

### 3.1 · Two gates, cheap before expensive

Curation happens **before** anything is durable, in two stages:

1. **Path gate** — `triage_allowed(path)` is one line: `path.startswith("/inbox/")`.
   Anything in `/work` or `/tool_out` never reaches the store, with no LLM call. The
   *writer* already signalled intent by choosing the folder.
2. **The store's own extraction** — an inbox note is posted as a message to its asset's
   thread, and Agent Memory's extraction LLM decides whether it becomes a memory. The
   *policy* is ours — `promote.CURATION_INSTRUCTIONS`, passed as
   `memory_extraction_custom_instructions` (it lives in the package so nb04 grades the
   same text): keep completed,
   factual observations; extract nothing from TODOs, dead ends, tool output, or work that
   could not be finished. There is no `hold` — an incomplete note is simply not kept.

```mermaid
stateDiagram-v2
  [*] --> N: written
  N --> S: producer stages (/inbox only)
  S --> P: extraction keeps it → one memory
  S --> D: extraction drops it
```

### 3.2 · Whole notes, verbatim, with provenance on the memory

The SDK's built-in extraction prompt asks for small *atomic* facts — the
chunk-and-reinterpret the review warned about. Our instructions override it for the
inbox thread: a kept note becomes **exactly one** `memory` record, **word for word**.
§4 checks that rather than trusting it, so an SDK change that stops honouring the
override fails loudly.

Provenance needs no table of ours. Each note is posted with `metadata={source_path,
revision, days_ago}`, and `memory_extraction_inherit_message_metadata` copies those keys
onto the memory. `list_memories(metadata_filter={"source_path": ...})` finds every memory
a note produced, and recall reads the observation's real age for recency weighting.

Re-runs are the one thing the store does not handle for us: it treats a re-posted note as
a new claim, not a duplicate, and keeps it as a fresh valid memory beside the old one. So
promotion is **idempotent per path** — it deletes what an earlier promotion of the same
path left before posting again.

### 3.3 · Supersession: the store's link step retires old facts

```mermaid
flowchart LR
  rep["repair note<br/>(pier 2 recoated)"] --> pn["promote_note → add_messages"]
  pn --> ex["extraction keeps it<br/>as one memory"]
  ex --> lk{"link step (our link instructions):<br/>does it replace an existing memory?"}
  lk -->|supersedes| st["defect.status → invalid<br/>(CITY_MEMORY_LINK)"]
  st --> q1["search(include_invalid_results=False,<br/>record_types=['memory']) → current belief"]
  st --> q2["search(num_hops=1)<br/>→ history, through the link"]
  st --> un["delete_record_link<br/>→ trigger revalidates"]
```

Nothing of ours decides supersession: the extraction call's link step compares each new
memory with the asset's existing ones and writes the relation. `supersedes`, `refines` and
`duplicates` flip their target to `invalid` (stored, hidden from current recall);
`contradicts` and `supports` leave both memories current. Recall must also pass
`record_types=["memory"]` — the thread's raw messages are searchable too, and messages are
never invalidated.

### 3.3b · The relation itself (§5c)

§5c looks at the relation the store wrote as **data**: one hop from the superseded memory
reaches what replaced it (*what did we believe before, and what changed it?*), deleting the
link revalidates the old memory, and `link_records` asserts a relation the store missed.
The store does the bookkeeping and the judging; we write the policy — the gate, the
curation and link instructions, the provenance keys — and check it.

This is also where the `CREATE TRIGGER` prerequisite comes from: the managed v13
schema carries a delete trigger on the link table that returns an invalidated
memory to `valid` when its invalidating relation goes away.

### 3.4 · The briefing, built from current memory (§6)

The payoff reads the asset's **valid** memories through the SDK — the superseded defect is
already `invalid`, so it is not reported as open — plus a few finding counts from SQL. The
model only narrates that input and cites each memory's `source_path`, so every claim traces
back to a note. The briefing is saved as a scratch note under `/briefings/` (outside the
inbox, so it is never promoted), which is what §7's fresh session resumes from.

The copilot's `remember` tool also owns the **asset id**: a model-supplied `harbor_bridge`
resolves to `Harbor Bridge`, and an unknown asset is refused. Before that, an agent note
could land in a different memory user, where neither supersession nor this briefing saw it.

## 4 · Notebook 03 — Context engineering

**Why:** the review's critique of the original context work was that it measured
**size**, not **fidelity**. A card that forgot everything looks best on a size
chart. The only interesting question is what the smaller context still *knows*.

### 4.1 · Compaction, measured by a probe

A deterministic 40-turn "season" (built from real findings, seeded, with **3
planted facts** at known turns) is folded into a versioned card whenever the
pending transcript hits a budget.

```mermaid
flowchart LR
  season["40-turn season<br/>(3 planted facts)"] --> L{"pending ≥ budget?"}
  L -->|yes| fold["LLM fold → merge_card"]
  fold --> ver[("HARNESS_CARD<br/>new version")]
  ver --> L
  ver --> probe["fidelity probe:<br/>ask for each planted fact<br/>36 turns later"]
```

The probe is the point: 36 turns after planting, ask the question whose answer
*requires* that fact, using **only the card**. Recall is scored, and the assertion
is deliberately **not 100%** — compaction really does lose things, and a notebook
that only passes when nothing is ever lost would be teaching a fiction.

### 4.2 · Making it forget on purpose — strength-based consolidation (§4b)

The base card is **additive** (nothing may leave) — which keeps the probe honest
but means it never compresses. §4b adds the two things a real card needs: a
**ceiling** (a reason to compress) and a principled rule for **what gives way**.
That rule is *not* age (TTL); it's **retrieval strength**.

```mermaid
flowchart LR
  fold["fold + reinforce touched facts"] --> over{"card > ceiling?"}
  over -->|yes| evict["evict weakest by fact_strength<br/>(reinforcement ↑, disuse ↓)"]
  evict --> gist["consolidate evicted → gist<br/>(keep the shape, lose specifics)"]
  over -->|no| keep["keep"]
```

A fact then lives in one of three states — the measure a hit/miss recall can't
express:

```mermaid
stateDiagram-v2
  [*] --> verbatim: held as a full card fact
  verbatim --> gist: evicted (weakest strength) → consolidated
  gist --> lost: gist kept the shape but dropped this specific
```

`fact_strength = (1 + reinforcements) * 0.5 ** (turns_since_reference / half_life)`
— the same half-life shape as recency recall in notebook 02, so the codebase carries
one decay model. The live result: over the same season the additive card grows past
the transcript while the strength card **holds its ceiling**, and `fact_status`
reports each planted fact as verbatim / gist / lost — a *measured* loss, not a
hidden one.

### 4.3 · Offloading with the agent in the loop

Compaction manages the conversation; offloading manages the **attachments**. A large
tool result is stored and the model is handed a **reference**, not the data.

```mermaid
sequenceDiagram
  participant A as Agent
  participant Ex as bulk_export tool
  participant B as HARNESS_BLOB
  A->>Ex: export(asset)
  Ex->>B: store 20KB payload
  Ex-->>A: "harness://blob/<id>"  (reference, not data)
  Note over A: notices a reference ≠ an answer
  A->>B: fetch_offloaded(id)
  B-->>A: full payload
  A-->>A: answer from what it went and got
```

The test is **behavioural**, not "the bytes are recoverable": the model must notice
the reference, fetch it, and use it. The check confirms the answer names an **opaque
`finding_id`** that only exists in the payload — proof it was actually read.

Finally, the **offload × promotion exclusion**: blob paths (`/tool_out/blob/…`) are
run through notebook 02's real gate and refused, while a genuine `/inbox` note still
promotes — so machine-generated dumps never masquerade as durable memories.

## 5 · Notebook 04 — Evals

**Why:** *measure what you claimed to fix, or you didn't fix it.* Five evals, each a
Langfuse dataset with scored traces, each grading a specific gap the earlier
notebooks addressed.

```mermaid
flowchart LR
  E1["1 · Promotion precision"] --> M1["nb02 curation gate"]
  E2["2 · Skill fidelity"] --> M2["nb01 distillation + faithfulness"]
  E3["3 · Skills-help"] --> M3["nb01 — does learning help?"]
  E4["4 · Card fidelity"] --> M4["nb03 compaction over a horizon"]
  E5["5 · Cost per correct"] --> M5["nb03 card vs transcript vs stateless"]
```

Each eval builds a labelled dataset, runs it through `dataset.run_experiment(task,
evaluators)` (Langfuse 4.x Experiments API), scores every item on the server, and
rolls the scores into one `check` plus a row in `HARNESS_EVAL`:

```mermaid
flowchart LR
  ds["labelled dataset"] --> exp["run_experiment(task, evaluators)"]
  exp -->|"per-item traces + scores"| agg["aggregate locally<br/>(evals.py metrics)"]
  agg --> chk["check(pass bar)"]
  agg --> tbl[("HARNESS_EVAL")]
```

- **Promotion precision** — precision/recall of nb02's real gate (path rule + the store's
  extraction under `promote.CURATION_INSTRUCTIONS`) on a signal+junk corpus, plus a check
  that every kept note became exactly one verbatim memory. Runs in a sandbox user
  (`_eval_promotion`) emptied before and after.
- **Skill fidelity** — an LLM judge scores distilled skills, with a **tampered
  control** proving the judge isn't a rubber stamp.
- **Skills-help** — the review's missing experiment: the agent *with* vs *without*
  harvested skills, judge-scored.
- **Card fidelity over a horizon** — planted facts probed after adversarial spacing.
- **Cost per correct answer** — card vs full transcript vs stateless, with variance.

This is where "through Langfuse" stops being optional: notebook 04 requires the
local stack up, because the evals *are* datasets with scored runs.

## 6 · The design principles, distilled

Six ideas recur across every notebook. If you internalize these, the code reads
itself:

1. **Pure decisions, effectful edges.** Rules live in `src/` (tested offline);
   SQL/LLM/Langfuse live in the notebooks. Bugs hide in the wiring, not the rules.
2. **Cheap check before expensive check.** A path prefix rejects junk before any LLM
   call; a distance floor drops off-topic tools before the model sees them.
3. **Verify against ground truth, not prose.** The judge re-queries the database; the
   offload test demands an id only present in the payload. Never trust the model's
   own summary of what it did.
4. **The tool owns policy; the agent supplies judgement.** `remember` decides *where*;
   the agent decides *whether*. Fewer things for the model to get wrong.
5. **Measure loss, don't hide it.** Compaction is allowed to forget — and the probe
   reports exactly what fell out (verbatim / gist / lost). An honest red beats a
   dishonest green.
6. **Idempotent + re-runnable.** Promotion replaces per path; resets clear the right
   tables; each notebook backfills what it needs. State that accumulates silently is
   the enemy (most bugs found in review were exactly this).

## 7 · Known gaps (honest limitations)

This project is a teaching harness, not production, and a deep review found real
gaps. Some are fixed; the rest are tracked. Kept here because pretending they don't
exist would violate principle #5.

| Area | Gap | Status |
|---|---|---|
| nb03 / `context.py` | `merge_card` wiped strength bookkeeping on re-list | **fixed** |
| nb01 | not re-runnable — `promoted='Y'` never reset, 2nd run fails at harvest | **fixed** — learned state resets at the registry DDL cell |
| nb04 | eval 5 crashed (`round(None)`) on the card-lost-a-fact case it exists to catch | **fixed** — reported `n/a (0 correct)`, drawn as no bar |
| nb04 | eval 3 passed vacuously on `0 ≥ 0` — didn't enforce "skills help" | **fixed** — both arms must be fully scored and one must succeed |
| nb02 | recency recall inert — sidecar never stores `days_ago` | **fixed** — `days_ago` travels as memory metadata (sidecar removed 2026-10-19) |
| nb03 | `fact_status` matches model-invented ids (tests coincidence, not retention) | identified |
| nb02 | `hold` notes are never re-triaged (stranded) | **moot** — `hold` removed with the triage LLM; incomplete notes are not kept |
| nb04 | eval 1 scores its own copy of a keep/discard LLM, not nb02's gate (now the SDK's extraction) | **fixed** 2026-10-19 — eval 1 runs the store's extraction under the shared `promote.CURATION_INSTRUCTIONS`; live: precision 1.00, recall 1.00, all kept notes verbatim |
| nb00 | Langfuse check is a false-green — `flush()` never raises, no `auth_check` | identified |
| nb01 | no skill-staleness signal at all: `schema_sha` was cut as the wrong layer, and its `tools_sha` replacement is designed but not built | deferred |

The pattern behind most of them is principle #6: **silent state accumulation** —
duplicates, un-reset flags, unpopulated columns — breaking a downstream assertion
one run later. That's the class of bug this kind of deep, trace-the-logic review is
best at catching.
